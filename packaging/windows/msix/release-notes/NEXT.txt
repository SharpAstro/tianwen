================================================================================
FIRST, AUDIT WHAT THE LISTING ALREADY CLAIMS
================================================================================
A standing step, not a formality, and the one most easily skipped because it is
about the LAST release rather than this one. Open the previous record's What's New
block and ask of every sentence whether it is still true. Three ways it goes wrong,
all of which have happened:

  - A claim goes STALE. 7.1.1627 told users to press O for the sky map; the sky
    then moved to its own key, so anyone following the live listing pressed O
    three times and never reached it.

  - A claim was WRONG WHEN WRITTEN. 7.1.1627 promised that a tilted galaxy rings
    as the disc it is. The overlay ellipse carried two independent reflections and
    was plausible at some angles and correct at none, which is how it passed
    review; it took an independent check (the direction to NGC 206, a star cloud
    lying ON M31's major axis) to see it.

  - A NUMBER was measured on the wrong artifact. 9.0.1940's draft claimed the
    download was "around 8 MB smaller" because four driver files removed from the
    install weigh 8.2 MB on disk. An msixbundle is compressed, so the figure
    crossed a compression boundary untested; measured on the bundle a user
    actually receives it was 150,270,411 bytes against 152,858,681, about 2.5 MB,
    and not even that was attributable to the drivers, since 376 commits sat in
    the same span. Caught before submission and the figure was dropped entirely.
    THE RULE: a number in the block is measured on the artifact the user receives,
    never on the inputs that built it. Prefer no figure to a qualified one.

Anything that fails the audit belongs in the block below as a CORRECTION, and it
outranks a new feature for the space: a user acting on a wrong instruction is worse
off than one who has not heard about a new button. Record the finding here too, so
the next release knows what was corrected and why.

NOT YET AUDITED FOR THIS RELEASE. The live listing is 9.0.1940, submitted
2026-09-21, and release-notes/9.0.1940.txt is its record. Audit these four claims,
which is what that listing now tells users:

  - The HDR button is gone, folded with Boost into one Tone button, and a line
    there names the display HDR the viewer cannot do. TRUE at submission. It goes
    stale the moment P2 of docs/plans/hdr-display.md ships real display HDR, which
    would make that line the wrong answer on a capable machine.
  - Hovering the sky atlas washes the object a click would select. Check the wash
    and the click still come from one resolver; two would drift apart silently.
  - Auto crop reads neither a drizzle stack's interior holes nor a dither strip
    down one edge as the edge of the stack. This sentence has now been widened
    twice and rewritten once; widen it a third time and rewrite it again instead.
  - Camera and focuser driver libraries are no longer installed with the viewer.
    Verify against the PACKAGE, not the build output: unzip the msixbundle and
    confirm neither payload carries ASICamera2.dll, qhyccd.dll, EAFFocuser.dll
    or EFWFilter.dll (EAFFocuser1.6.dll and EFW1.7.dll before ZWOptical.SDK 6.0).
    It was 0 of 4 across both x64 and arm64 payloads in 9.0.1940.

WHAT'S NEW  (Partner Center copy - paste between the two marker lines VERBATIM)
================================================================================
Measured at bake time: {{WHATSNEW_CHARS}} characters, or {{WHATSNEW_CHARS_CRLF}} if
the paste turns the newlines into CRLF. The cap is 1500 and the bake FAILS over it,
so this number is always true of what is below. Do not paste the DETAIL section.

Shape that has worked three times: two or three HEADED sections carrying the
release, then an "Also in this release" list of one-line bullets. Corrections go
first within their group. Say what the user can now DO, in their words, not ours.

Leave the sentinel line in place until this is written. The bake looks for
"WRITE THIS BEFORE DISPATCHING" and WARNS when it is still there, which is what
lets a binary-only dispatch pass a packaging lane it owes nothing to. Deleting the
sentinel without writing copy is the one thing that turns that warning off while
leaving the listing empty.

----- BEGIN WHAT'S NEW -----
WRITE THIS BEFORE DISPATCHING
----- END WHAT'S NEW -----

Which way to cut if it goes over: the headed sections are the release and the
bullets are the tail, except that a bullet CORRECTING a live claim is cut last of
all. Record here what was left out, so the next writer knows what is owed rather
than rediscovering it.

================================================================================
Carry the previous record's list forward item by item and mark each one Unchanged,

Carried forward from 9.0.1940 (2026-09-21) UNREVIEWED. Re-check each at dispatch.

  P21    Single-channel views of a mosaic show the raw mosaic, not the separated
         colour planes (a shader change).

  P11.2  The ? panel names missing SAS AI weights but cannot fetch them from a
         Store install.

  P9/P10 Unconfirmed, neither reproduced since first report.

  SPCC   Broadband only; narrowband blocked on data (per-star Gaia DR3 xp_sampled
         spectra), not on maths.

  Layout Below about 730 px of window width the image pane reaches zero width and
         the histogram overlay lands on the file list.

  About  The About banner concatenates run attempt onto the version (9.0.NNNN1 for
         attempt 1); FileVersion is correct.

  CFA    The SER frame-by-frame histogram sits a mosaic out.

  HDR    A KNOWN GAP rather than a bug: the Tone panel names display HDR and cannot
         offer it, and the reason it gives is about the viewer rather than the
         user's GPU, because nothing in the build asks the GPU what its surface
         offers. Closed by P2 of docs/plans/hdr-display.md.

  Holes  The number of interior holes filled at load is on the document
         (AstroImageDocument.InteriorHolesFilled) but is not shown in the info
         strip or the status bar, so a user cannot see that pixels were
         interpolated.

         settles, or settles only within one window and not a wider one, is
         DECLINED and left uncropped. Correct, but it looks like auto crop doing
         nothing on a frame that visibly has a ramp, and nothing says which edges
         were declined or why.

SUBMISSION
================================================================================
  1. Download the package and this record from the run that baked it:
       gh run download {{RUN_ID}} -n msix-store-package
       gh run download {{RUN_ID}} -n msix-release-notes
     The bundle is about 145 MB. Retention is 30 days on both. The notes artifact
     holds this record AND whats-new-{{VERSION}}.txt, which is the Partner Center
     copy alone, so nothing has to be selected out of a 20 KB file by eye.
  2. Upload AstroPhotoViewer.msixbundle to the draft submission for
     Store ID 9PMDZP16TGBG. It is unsigned by design; the Store re-signs after
     certification, so it cannot be installed by double-clicking.
  3. Paste whats-new-{{VERSION}}.txt into "What's new in this version". It is
     exactly the bytes the field should receive, markers and commentary excluded.
  4. If the bundle was signed locally for testing, re-download before uploading;
     signing edits the package in place.
  5. Commit this baked file as release-notes/{{VERSION}}.txt and reset NEXT.txt.

  A re-dispatch takes the NEXT run number, so the baked record and the package
  agree only within one run. If a run has to be re-run, use the new run's artifacts
  rather than editing the number inside an older record.

  If the copy has to change AFTER the bake, as it did for 9.0.1940, re-bake locally
  with the same -Version and -RunId rather than re-dispatching: the notes ride
  beside the bundle and never inside it, so the package stays valid. Say so in the
  record, because the run's own artifact then holds a superseded block and the
  committed record is the authority.
