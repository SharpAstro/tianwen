THIS RELEASE IS 9.0, AND THE JUMP IS NOT ABOUT THE VIEWER. 9.0 is breaking for
TianWen.Lib (its geometry types are its own, the dependency floor moves two majors,
and the ZWO and QHYCCD drivers move to a package of their own), and a Store user

================================================================================
FIRST, AUDIT WHAT THE LISTING ALREADY CLAIMS
================================================================================
A standing step, not a formality, and the one most easily skipped because it is
about the LAST release rather than this one. Open the previous record's What's New
block and ask of every sentence whether it is still true. Two ways it goes wrong,
both of which have happened:

  - A claim goes STALE. 7.1.1627 told users to press O for the sky map; the sky
    then moved to its own key, so anyone following the live listing pressed O
    three times and never reached it.

  - A claim was WRONG WHEN WRITTEN. 7.1.1627 promised that a tilted galaxy rings
    as the disc it is. The overlay ellipse carried two independent reflections and
    was plausible at some angles and correct at none, which is how it passed
    review; it took an independent check (the direction to NGC 206, a star cloud
    lying ON M31's major axis) to see it.

Anything that fails the audit belongs in the block below as a CORRECTION, and it
outranks a new feature for the space: a user acting on a wrong instruction is worse
off than one who has not heard about a new button. Record the finding here too, so
the next release knows what was corrected and why.

Audited 2026-09-15 against 8.0.1716 (live in the Store the same day): every
sentence still holds. The auto-crop bullet ("no longer mistakes a dead pixel for
the edge of the stack") is TRUE but now understates the rule, which since 8.1 also
covers a drizzle hole; that is an extension, not a correction.

Re-audited 2026-09-21, the draft having sat unreleased for six days while 9.0 work
landed. 8.0.1716 is still the live listing and every sentence in it still holds.
The auto-crop bullet now understates the rule a SECOND way: since the edge-walk
rework it also declines a gradient that merely goes quiet, and trims a dither strip
deeper than the old cap. Still an extension rather than a correction, and the block
below restates the crop claim from scratch rather than patching it, because three
separate widenings of one sentence is how a claim stops matching the code.

One CORRECTION is in this release, and it leads the block for that reason: the
toolbar's "HDR" button never did HDR. It applies a soft knee after the stretch and
inside [0, 1], so it compresses highlights into ordinary white and never asks the
panel for a nit above it. No live listing sentence says so -- the audit above is
about what was WRITTEN -- but the button itself was the claim, which is worse: a
user with an HDR display read it as a promise about their screen. Named here so the
next release knows the label changed and why.

----- BEGIN WHAT'S NEW -----
The HDR button was never HDR
It softens the clipping in the brightest parts of the picture, which is useful, but it never asks your display for anything brighter than an ordinary window's white. On an HDR screen the name promised something it could not deliver. It now sits with Boost under one Tone button, alongside a line naming the display HDR this viewer cannot do yet. B and H still step them, and the picture itself is unchanged.

The sky atlas shows what a click will take
Rest the pointer on a crowded field and a soft wash marks the object a click would select, so you can tell which of several overlapping markers you are about to open.

Auto crop keeps the whole frame
It no longer reads a drizzle stack's interior holes, or a dither strip down one edge, as the edge of the stack. A fully covered master is no longer cut to half its width, and the holes are filled from their neighbours when the file opens, so they neither show as black specks nor skew the statistics.

Also in this release
- Saving a frame demosaiced with MHC is about ten times faster, and a colour frame opens twice as fast.
- Menus stay under their toolbar button when you resize or maximise, never run off a narrow window, and the wheel scrolls a long one instead of zooming the picture.
- Camera and focuser driver libraries this viewer never had a use for are no longer installed with it.
----- END WHAT'S NEW -----

Which way to cut if it goes over: the headed sections are the release and the
bullets are the tail, except that a bullet CORRECTING a live claim is cut last of
all. Record here what was left out, so the next writer knows what is owed rather

Left out of this one, with 86 characters of headroom remaining and each judged not
worth the space: the object overlay can now be narrowed to objects that have a
photo, and the same filter applies to what a click can select (a sub-setting of a

something the user never saw as slow invites the question); and every headless
render obeys the viewer's own stretch rules now, which matters to `tianwen stack`
and the gallery rather than to anyone running this app.


DETAIL
================================================================================
The evidence behind the block, by area, citing commits. Cite a commit by its
SUBJECT in quotes if it has not landed yet -- every PR merges by rebase, so a hash
written before its PR lands is rewritten on landing.

Auto crop and drizzle holes (issue #250; "fix(imaging): an interior drizzle hole is
not a canvas ring, and what the crop keeps now has a number", PR #262)
  Absence is border-reachable for NaN exactly as it was for zero. Measured on the
  file that reported it: 1,856 NaN in 20 components on a 3024 x 3025 BayerDrizzle
  master took a 99.94 percent covered frame to 0.528 of its canvas. 53 of 79
  masters in one bake carry interior holes, every BayerDrizzle one.
  Image.FillInteriorHolesInPlace runs from AstroImageDocument.AdoptImageAsync
  before any statistic; the canvas ring is never filled. The count is on
  AstroImageDocument.InteriorHolesFilled and is NOT yet shown anywhere in the UI
  (see KNOWN ISSUES). This is what would have made the release 8.1: new public
  TianWen.Lib API on an 8.0 already dispatched ("build: 8.1, because
  FillInteriorHolesInPlace is new public API on an 8.0 already dispatched"). It
  ships as part of 9.0 instead, 8.1 never having been dispatched.

The edge walk behind the crop, added since the 8.1 draft (issue #71, PR #327)
  Second half of the same user-facing sentence, and a different mechanism. The
  walk that finds an uncovered border read MaxTrimFraction twice, as the cap on
  what an edge may lose AND as the depth it was allowed to look, coupled to a fixed
  reference band. Swept on four real masters, every edge of every master went to
  0 px at ratio 1.00 from 0.08 upward: the knob's useful range ended at about 0.075
  with nothing saying so, so turning it up to reach a deep dither strip silently
  disabled the crop entirely. Cap, search depth and reference are three settings
  now. The walk also profiles to 1.5x its search and applies the settle rule at
  both widths, because within one window a real border and a gradient that happens
  to go quiet are indistinguishable, and reports Unconfirmed rather than folding
  the two into one verdict; over a 139-master corpus that is 7 borders to 15
  gradients. The user-visible half is only "a dither strip down one edge comes off
  and a gradient is left alone"; the rest is in CHANGELOG 9.0.

The sky atlas hover wash, added since the 8.1 draft ("feat(atlas): say what a click
would take, and narrow the overlay to objects with a photo")
  The complaint was that on a field of overlapping markers nothing told you which
  object a press would land on. The load-bearing property is that the wash and the
  click come from ONE resolver (SkyMapSearchActions.TryResolveHit): two hit tests
  written the same way is exactly how a wash over one object and a panel about
  another happens, which is worse than no wash. Ctrl is deliberately not honoured
  by the hover, the modifier being read at the press. One FillEllipse, drawn first
  of the annotation layers, so a pointer resting over the search modal or the layer
  palette is harmless. At most one resolve per painted frame; the resolve was made
  allocation-free on the way (389 us / 225 KB over bare star field to 157 us at
  1 degree FOV and about 1.7 us by 60, 0 B on every row), which is why it is
  affordable per frame at all but is NOT claimed in the block.

The HDR button, and the fold that replaced it ("feat(viewer): boost and the
highlight soft clip share one Tone popover, and it names the HDR it cannot do",
docs/plans/hdr-display.md P1)
  Image.ApplyHdr is a soft knee applied AFTER the MTF and INSIDE [0, 1]: it trades
  contrast for gradient above the knee and never emits a value above SDR white.
  Nothing about it needs an HDR panel, and the label was the only thing in the
  toolbar promising one. Folded with Boost into ToolbarAction.Tone on the terms
  Calibrate and SPCC folded into the white-balance popover; the two preset ladders
  became continuous dials, each stating its own precondition; a greyed block names
  display HDR with a reason about the VIEWER, since nothing asks the GPU yet. The
  MATH did not move -- image.frag, Image.ApplyHdr, StretchTests_NewPipeline and
  GpuStretchPipelineTests are byte-for-byte what they were. Real display HDR is
  measured and possible on the laptop's hardware (Qualcomm Adreno driver
  31.0.170.0, scRGB on the Surface OLED, confirmed with SdlVulkan.Renderer's
  HdrProbe) and is P2 to P4 of that plan, not in this build.

Faster demosaic and statistics ("perf(imaging): a plane stays float[,]; the hot
loops stop reading it as [y, x]", PR #263)
  The MHC row is the one order-of-magnitude claim: 27 to 85 ms before, 6.0 to 16 ms
  after on a real 3008 sq frame, the worst after-reading under the best before. The
  luminance statistic (GetLumaStretchStatsAsync) halved: 8.36 to 4.01 ms at 1024 sq,
  26.7 to 14.2 at 2048 sq. The 2x2 mono fold did not measurably change and is NOT
  claimed. Lanczos3 and the CFA split/merge also gained but reach the viewer only
  through stacking and gradient removal, so they are not in the block either. All
  numbers and their caveats: docs/architecture/image-pipeline.md, "How a plane is
  READ". NOTE the multipliers are per-machine: these were taken on win-arm64 and
  the block states them as ratios, not times, for that reason.

Toolbar menus and the window (PR #310; "fix(viewer): a toolbar menu follows its
button on resize, and the wheel scrolls a long one" and "fix(viewer): a menu is
never wider than the window, so it hangs from its button")
  Three defects in one place, all found testing the DIR.Lib 10.2 build on
  2026-09-19. An open menu was placed once, at open, so a resize or maximise left
  it where the button USED to be; it is now re-anchored every frame from the
  button painted that frame. The standalone host routed only presses through its
  router, so the wheel over a long menu (the ? shortcuts page) zoomed the picture
  instead of scrolling the list; moves, releases and the wheel now go through it
  too. And a menu wider than the window was clamped on screen by shifting it
  sideways off its button; its width is now capped at the window's, so it always
  hangs from the button. ViewerE2ETests pins all three at DPI 1 and 1.5.

The package is smaller, added since the 8.1 draft ("refactor(devices): the vendor
drivers are their own assembly, so a viewer stops shipping 8.2 MB of them")
  8.0.1716 shipped ASICamera2.dll, qhyccd.dll, EAFFocuser1.6.dll and EFW1.7.dll
  inside an image viewer that connects no hardware and registers no device source.
  They arrived through the reference graph and nothing downstream could refuse
  them: the SDK projects mark their natives CopyToOutputDirectory deliberately,
  MSBuild propagates that to every transitive consumer, and trimming reasons about
  MANAGED reachability while a native library is an opaque blob a DllImport may
  resolve by name at run time. The drivers now live in TianWen.Devices.Native,
  which the viewer does not reference. Verified on a clean Release rebuild: 0 of
  the four in the viewer's output against 61 DLLs in total, with the GUI unchanged.
  Verified again IN THE SHIPPED PACKAGE, which is the check that counts: both
  payloads of AstroPhotoViewer.msixbundle (x64 and arm64) carry 41 files and 7
  DLLs, and none of the four is among them.
  THE BLOCK CARRIES NO SIZE NUMBER, and the first draft of it did. It said "around
  8 MB smaller", which is wrong twice over. 8.2 MB is the on-disk payload of the
  four files, and the bundle is compressed, so the download delta is much smaller:
  measured, 150,270,411 bytes against 8.0.1716's 152,858,681, about 2.5 MB. And
  even that 2.5 MB cannot be attributed to the drivers, because 376 commits of
  other change sit in the same span. A user does not care whether it is 2 MB or 8,
  so the claim is now about what is no longer installed and carries no figure at
  all. The general rule, since this is the second time a size has been restated
  across a compression boundary: a number in the block has to be measured on the
  artifact the user receives, not on the inputs that built it.

Also landed in this span but NOT in the block, being invisible here: every headless
render (the master_*.png companion of `tianwen stack`, the dataset gallery) now
resolves its stretch through the same rule the viewer always used, which changed
five of 139 gallery cards; per-pixel sidecars are quantised before gzip (112.80 MB
to 1.71 MB on a real coverage map); `stack` and the dataset bake agree on which
frames are fit to integrate; and a camera whose model number hides its sensor die
now finds its QE curve (73.5 to 92.3 percent of the reference archive's frames).
None of these is reachable from this app.


KNOWN ISSUES IN THIS BUILD
================================================================================
Carry the previous record's list forward item by item and mark each one Unchanged,
closed, or changed. A known issue that quietly vanishes between records is one
nobody decided about.

Carried forward from 8.0.1716 on 2026-09-15, re-checked 2026-09-21.

  P21    Unchanged, still BACKLOG. Single-channel views of a mosaic show the raw
         mosaic, not the separated colour planes (a shader change).

  P11.2  Unchanged. The ? panel names missing SAS AI weights but cannot fetch them
         from a Store install.

  P9/P10 Unchanged, still unconfirmed, neither reproduced since first report.

  SPCC   Unchanged. Broadband only; narrowband blocked on data (per-star Gaia DR3
         xp_sampled spectra), not on maths.

  Layout Unchanged. Below about 730 px of window width the image pane reaches zero
         width and the histogram overlay lands on the file list.

  About  Unchanged. The About banner concatenates run attempt onto the version
         (9.0.NNNN1 for attempt 1); FileVersion is correct. Worth re-reading at
         submission: the version shown will now start 9.0, and a reviewer
         comparing it against the Store's 8.0.1716 sees a two-part jump.

  CFA    Unchanged. The SER frame-by-frame histogram sits a mosaic out.

  HDR    Unchanged from the 8.1 draft, and a KNOWN GAP rather than a bug: the Tone
         panel names display HDR and cannot offer it. The reason it gives is about
         the viewer ("not yet; the viewer always presents SDR") and NOT about the
         user's GPU, because nothing in the build asks the GPU what its surface
         offers. A user whose machine can do it is told the same thing as one whose
         cannot. Deliberate for this release; P2 of the plan closes it.

  Holes  Unchanged from the 8.1 draft. The number of interior holes filled at load
         is recorded on the document (AstroImageDocument.InteriorHolesFilled) but
         not shown in the info strip or the status bar, so a user cannot see that
         pixels were interpolated. The block above therefore says the holes are
         filled and does not promise a count.

  Crop   New, and a deliberate refusal rather than a defect: an edge whose profile
         never settles, or settles only within one window and not a wider one, is
         DECLINED and left uncropped. That is the correct answer (trimming to an
         unconfirmed depth would cut real data), but to a user it looks like auto
         crop doing nothing on a frame that visibly has a ramp. Nothing in the UI
         says which edges were declined or why.
